# 기관용 근태관리

기관용 근태관리는 직원이 휴대전화나 PC에서 출근과 퇴근을 기록하고, 관리자가 기관별 근태와 수정 요청, 월 마감, 변경 이력을 관리하는 오픈소스 웹앱입니다.

급여 계산 프로그램이 아닙니다. 출퇴근 사실과 근무 장소 확인, 누락 기록 보정, 월별 보관에 집중한 1차 버전입니다.

## 핵심 기능

- 직원 로그인, 출근과 퇴근 기록, 이번 달 기록 확인
- 출퇴근 버튼을 누르는 순간에만 GPS 확인
- 사업장 기준점과 거리, 정확도, 반경 내외 판정
- GPS와 사무실 공인 IP를 기준으로 일반 출근, 직출, 일반 퇴근, 직퇴 자동 구분
- 사무실 공인 IP는 브라우저 입력값이 아니라 Cloudflare 서버가 확인한 접속 IP로 판정
- 자정을 넘긴 근무는 전날의 미퇴근 기록에 이어서 퇴근 처리
- 사업장 밖 출퇴근과 위치 확인이 어려운 경우 사유를 포함한 기록 제출
- 숙박 출장과 관리자 승인 예외 근무 기간 등록
- 수정 요청, 승인, 반려, 추가정보 요청
- 관리자 대시보드와 월별 근태표
- 직원별 연차 부여기간과 잔액, 부여내역 수정과 사유가 남는 삭제, 대체휴무 적립과 만료일 관리
- 대체휴무 잔액 초과 승인 차단과 사유가 남는 사용기한 연장
- 대체휴무 적립 총량, 사용 누계, 사용 가능 잔액, 기한 만료 잔액을 관리자와 직원 화면에서 구분 표시
- 월별 승인 시간외에서 같은 달 발생 대휴 적립분의 실제 사용시간만 빼서 `대휴 제외 시간외`를 표시하고, 지난달 발생 대휴 사용은 이번 달 시간외에서 차감하지 않음
- 연차에서 차감하지 않는 특별휴가 신청과 승인
- 외부교육은 날짜별 09:00 출근, 18:00 퇴근 기록으로 생성하며 출근부 비고에는 교육내용을 표시하지 않음
- 시간외근무는 퇴근시각이 아니라 점심시간과 승인 휴가를 제외한 실제 근무가 8시간을 넘은 분량으로 계산
- 최초 1시간은 모두 채워야 하며 이후 30분 구간은 1분이라도 넘으면 다음 30분까지 올림 인정
- 월 마감, 최고관리자 마감 해제, 감사 로그
- CSV, 엑셀, 인쇄 또는 PDF 저장
- Supabase 인증과 Row Level Security
- 모바일 홈 화면에 추가할 수 있는 PWA 기본 구조
- Supabase 설정 전에도 화면과 흐름을 확인할 수 있는 데모 모드
- 휴대전화와 개인 PC에서는 로그인 상태를 유지하고, 세션이 실제로 만료되면 즉시 로그인 화면으로 전환
- 본인 비밀번호 변경과 최고관리자 임시 비밀번호 설정은 Supabase 허용 최저값인 6자부터 입력 가능

## 개인정보 보호 설계

- 상시 위치추적과 백그라운드 GPS 수집 기능이 없습니다.
- 출근 또는 퇴근 버튼을 누를 때만 브라우저 위치 권한을 요청합니다.
- 원본 위도와 경도는 일반 근태기록과 분리된 `attendance_locations` 테이블에 저장합니다.
- 일반 관리자는 반경 내외, 거리, GPS 정확도, 위치 확인상태만 봅니다.
- 원본 좌표는 해당 직원과 최고관리자만 볼 수 있도록 정책을 분리했습니다.
- 사업장 밖 출퇴근은 직출 또는 직퇴와 관리자 확인 필요 상태로 기록하며, 오류나 부정근태로 확정하지 않습니다.
- 위치 정확도가 낮거나 위치를 확인할 수 없으면 사유를 받아 관리자 확인 대상으로 저장합니다.
- 관리자 수정도 기존 값을 덮어쓰고 끝내지 않으며 감사 로그에 전후 값을 보존합니다.
- 프론트엔드에는 Supabase 서비스 역할 키를 사용하지 않습니다.

## 적용한 기본값

요구사항이 확정되지 않은 부분에는 다음 값을 적용했습니다.

- 시간대는 `Asia/Seoul`입니다.
- 기본 근무일은 월요일부터 금요일입니다.
- 기본 근무시간은 09:00부터 18:00까지입니다.
- 기본 휴게시간은 60분입니다.
- 기본 GPS 허용 반경은 100m입니다.
- GPS 정확도가 100m보다 낮으면 관리자 확인 대상으로 분류합니다.
- 한 직원은 하루에 출근과 퇴근을 각각 한 번 기록합니다.
- 출근 없이 퇴근할 수 없습니다.
- 월 마감 전 대기 중인 수정 요청이 있으면 마감하지 않습니다.
- 마감 해제는 최고관리자만 가능하며 사유를 반드시 남깁니다.
- 대한민국 공휴일 자료는 자동으로 외부에서 수집하지 않습니다. 운영 전 `holidays` 테이블에 기관 적용 공휴일을 입력해야 합니다.
- 직원별 예외 일정은 `employee_schedule_overrides` 테이블로 관리합니다.
- 숙박 출장과 승인 예외 근무는 `attendance_exceptions` 테이블에 승인자와 기간을 기록합니다.

## 폴더 안내

```text
app/                    화면과 사용자 기능
lib/                    위치 판정, Supabase 연결, 자료 형식
public/                 PWA 설정과 공개 정적 파일
supabase/install_current.sql  신규 기관용 현재 통합 설치 SQL
supabase/schema.sql     기본 데이터베이스 구조의 원본
supabase/seed.sql       최초 관리자와 시험 계정 설정 예시
tests/                  자동 점검
.env.example            환경변수 예시
```

## 로컬 실행

Node.js 22.13 이상과 pnpm이 필요합니다.

```bash
corepack enable
pnpm install
copy .env.example .env.local
pnpm dev
```

브라우저에서 표시된 로컬 주소를 엽니다. `.env.local`에 Supabase 값이 없으면 데모 모드로 실행되며 직원 화면과 관리자 화면을 전환해 기능을 확인할 수 있습니다.

## Supabase 설정

1. Supabase에서 새 프로젝트를 만듭니다.
2. SQL Editor를 열어 `supabase/install_current.sql` 전체를 한 번 실행합니다.
3. 실행 결과가 `Success. No rows returned`인지 확인합니다.
4. Authentication의 Email 로그인을 활성화합니다.
5. Project Settings, API에서 Project URL과 anon public key를 확인합니다.
6. `.env.local`에 아래 값을 입력합니다.

이미 운영 중인 기관 데이터베이스에는 `supabase/upgrade_leave_balances_and_special_leave.sql` 전체를 SQL Editor에서 한 번 실행합니다. 이 파일은 연차와 대체휴무 잔액, 특별휴가, 외부교육 09:00부터 18:00까지의 근무기록 전환을 함께 적용합니다.

```env
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_SUPABASE_PUBLISHABLE_KEY
```

기존 프로젝트의 anon public key도 `NEXT_PUBLIC_SUPABASE_ANON_KEY`로 사용할 수 있습니다. 서비스 역할 키는 절대로 `NEXT_PUBLIC_` 환경변수나 브라우저 코드에 넣지 않습니다.

### 기관 계정으로 새로 연결할 때

1. 기관 Supabase의 SQL Editor에서 `supabase/install_current.sql` 전체를 한 번 실행합니다.
2. 기존 운영 프로젝트를 보완하는 경우에는 전체 설치 파일을 다시 실행하지 않습니다. 아직 적용하지 않았다면 `supabase/upgrade_secure_clock_and_overnight.sql`을 먼저 실행하고, 이번 기능용 `supabase/upgrade_batch_training_actual_overtime.sql`을 실행합니다.
3. Authentication에서 관리자 1명과 직원 5명의 사용자를 생성합니다.
4. `supabase/seed.sql`의 관리자 이메일을 기관 관리자 이메일로 바꾼 뒤 실행합니다.
5. 앱의 `NEXT_PUBLIC_SUPABASE_URL`과 `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`를 기관 프로젝트 값으로 교체합니다.

기관 대표메일로 최고관리자를 교체할 때는 새 사용자를 먼저 만든 뒤 `supabase/migrate_super_admin.sql`을 사용합니다. 실제 관리자 이메일은 SQL 파일이나 GitHub에 저장하지 않고, Supabase SQL Editor에서 실행할 때만 자리표시자를 바꿉니다. 기존 관리자는 변경 이력 보존을 위해 삭제하지 않고 비활성화합니다.

출퇴근 저장 시 오류코드 `23514`가 나오면 기존 데이터베이스의 허용값 규칙이 현재 앱보다 오래된 상태입니다. `supabase/repair_attendance_check_constraints.sql` 전체를 SQL Editor에서 한 번 실행해 현재 위치 상태와 관리자 확인 상태를 허용하도록 맞춥니다.

같은 날짜의 출퇴근 기록을 관리자가 삭제한 뒤 직원이 다시 출근할 때 `attendance_records_check1` 오류가 나오면 삭제된 행의 이전 퇴근값이 남은 경우입니다. `supabase/repair_reclock_after_delete.sql`을 한 번 실행하면 기존 삭제 이력은 보존하면서 새 출근 시 이전 퇴근값만 초기화합니다.
6. 기관 GitHub의 빈 비공개 저장소를 새 원격 저장소로 연결하고 현재 코드를 올립니다.
7. 새 배포 환경에도 같은 기관 Supabase 주소와 공개용 키를 등록한 뒤 배포합니다.
8. 관리자 설정 화면에서 사업장 위치와 사무실 공인 IP를 새로 저장합니다.

개인 Supabase의 시험 기록을 기관 Supabase로 옮길지는 별도로 결정합니다. 실제 직원 기록이 없다면 빈 데이터베이스에서 시작하는 편이 단순합니다. 실제 근태기록이 있다면 원본 기록, 위치정보, 수정 요청, 변경 이력을 포함한 이전 계획을 먼저 세워야 합니다.

현재 운영 중인 기관 앱을 업데이트할 때는 적용하지 않은 보완 SQL을 파일 생성 순서대로 한 번씩 실행합니다. 이번 다중 직원 등록, 외부교육, 실제 시간외근무와 중간 휴가 계산은 `supabase/upgrade_batch_training_actual_overtime.sql`을 실행해야 사용할 수 있습니다. 출퇴근 서버 검증용 `supabase/upgrade_secure_clock_and_overnight.sql`을 아직 실행하지 않았다면 이 파일을 먼저 적용합니다.

월 마감을 해제했는데도 과거 근태기록을 수정할 수 없다면 `supabase/fix_admin_edit_after_reopen.sql`을 실행합니다. 이 파일은 월 마감 상태와 개별 기록의 마감값을 다시 맞추고 과거 근태상태의 수정 허용값을 보완합니다.

관리자가 출근 또는 퇴근시각을 비운 뒤 직원이 같은 버튼을 다시 눌렀을 때 중복 기록 안내가 나오면 `supabase/fix_reclock_after_admin_time_clear.sql`을 실행합니다. 이 파일은 시각을 비울 때 해당 중복 방지 이벤트도 함께 정리하여 직원이 다시 출근 또는 퇴근을 기록할 수 있게 합니다.

대체휴무 적립시간을 시간외근무 승인시간과 별도로 실제 추가근무 전체에서 인정하려면 `supabase/fix_comp_time_recognition_rule.sql`을 실행합니다. 대체휴무는 최초 1시간부터 인정하고 이후에는 30분 단위로 적립하며, 시간외근무의 하루 4시간과 주 12시간 한도에는 대체휴무 적립시간을 합산하지 않습니다.

### 기관 GitHub와 기관 Cloudflare 연결

기관 도메인이 없어도 Cloudflare Workers의 기본 `workers.dev` 주소를 사용할 수 있습니다. Cloudflare 계정은 기관 이메일로 만들고 기관 GitHub 저장소를 연결합니다.

1. Cloudflare Workers에서 GitHub 저장소 연결을 선택합니다.
2. 기관 GitHub의 비공개 `Attendance-Management` 저장소만 접근 허용합니다.
3. 빌드 명령은 `pnpm run build`, 배포 명령은 `pnpm exec wrangler deploy`로 지정합니다.
4. 빌드 변수로 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`를 등록합니다.
5. Worker의 실행 환경변수에는 `NEXT_PUBLIC_SUPABASE_URL`을, 비밀값에는 `SUPABASE_SECRET_KEY`를 등록합니다.
6. 배포 후 만들어진 `workers.dev` 주소를 Supabase Authentication의 Site URL과 Redirect URLs에 등록합니다.

`SUPABASE_SECRET_KEY`는 서버에서 실제 접속 IP를 확정하는 출퇴근 저장, 직원 계정 생성, 직원 비밀번호 초기화에 사용합니다. GitHub Actions 로그, 저장소 파일, 브라우저 환경변수에는 넣지 않습니다. 이 값이 없으면 보안상 출퇴근 저장을 허용하지 않습니다.
첫 배포는 Worker를 생성하기 위한 단계이며 환경값 등록 전에는 데모 화면이 나올 수 있습니다. Worker가 생성되면 빌드 변수와 실행 환경변수, 비밀값을 등록하고 다시 배포합니다.

### 로그인 유지

현재 로그인은 같은 브라우저에 유지됩니다. 휴대전화와 개인 PC 모두 새로고침하거나 브라우저를 닫았다 열어도 로그아웃하거나 관리자가 세션을 해제하기 전까지 다시 로그인하지 않아도 됩니다. 일시적인 통신 오류만으로 저장된 로그인 정보를 삭제하지 않으며, 세션이 실제로 만료되거나 로그아웃되면 기존 앱 화면을 닫고 로그인 화면으로 전환합니다. 위치 확인은 출퇴근 장소를 확인하는 수단일 뿐이며, 사용자가 누구인지 확인하는 로그인을 대신하지 않습니다. 공용 컴퓨터에서는 사용 후 반드시 직접 로그아웃합니다.

### 이메일 설정

내부 운영에서는 이메일 확인을 사용하는 편이 안전합니다. Supabase Authentication의 Site URL과 Redirect URLs에 실제 배포 주소를 등록합니다. 비밀번호 재설정 메일도 이 주소를 사용합니다.

## 최초 최고관리자 생성

1. Supabase Authentication, Users에서 관리자 계정을 생성합니다.
2. 계정 생성 시 `profiles` 행이 자동으로 만들어집니다.
3. `supabase/seed.sql`의 `ADMIN_EMAIL_REPLACE_BEFORE_RUN`을 기관 관리자 이메일로 로컬에서만 바꿉니다.
4. SQL Editor에서 관리자 부분을 실행합니다.
5. `profiles.role`이 `super_admin`인지 확인합니다.

최고관리자는 일반 관리자 지정, 월 마감 해제, 원본 좌표 열람, 직원 비밀번호 초기화 권한을 가집니다. 실제 관리자 이메일은 저장소에 커밋하지 않습니다.

## 비밀번호 변경과 초기화

- 로그인한 사용자는 왼쪽 메뉴 아래의 열쇠 버튼에서 본인 비밀번호를 변경합니다.
- 관리자는 로그인 화면에서 기관 이메일로 비밀번호 재설정 안내를 받을 수 있습니다.
- 최고관리자는 설정 화면에서 직원 계정을 삭제하지 않고 임시 비밀번호를 설정할 수 있습니다.
- 출퇴근 저장, 직원 계정 생성, 직원 비밀번호 초기화 서버 기능에는 `SUPABASE_SECRET_KEY`가 필요합니다. 운영에서는 호스팅 서비스의 비밀 환경변수에만 저장하고 GitHub나 브라우저 코드에는 넣지 않습니다. 로컬 시험에 사용할 경우에는 Git에서 제외된 `.env.local`에만 둡니다.
- 임시 비밀번호를 전달받은 직원은 로그인 후 본인 비밀번호로 다시 변경합니다.

## 사업장 좌표와 반경 설정

관리자 화면의 설정에서 사업장명, 위도, 경도, 허용 반경을 입력합니다.

초기 `seed.sql`의 좌표는 화면 시험용 예시입니다. 실제 운영 전 정확한 사업장 좌표로 변경해야 합니다. 좌표를 얻을 때 내담자 관련 시설이나 비공개 장소의 정확한 주소가 공개 자료에 남지 않도록 주의합니다.

허용 반경은 50m, 100m, 150m, 200m 중 선택할 수 있습니다. 건물 구조와 휴대전화 GPS 편차를 고려해 시험 운영 후 확정합니다. 정확도가 낮은 기록은 반경 밖 여부와 별개로 관리자 확인 대상으로 봅니다.

## 직원 계정 추가

1. Supabase Authentication, Users에서 이메일 계정을 생성합니다.
2. SQL Editor 또는 관리자용 내부 절차로 해당 `profiles` 행의 이름, 사번, 부서 값을 수정합니다.
3. `role`은 `employee`로 유지합니다.
4. 최초 로그인 안내와 위치정보 처리 안내를 직원에게 전달합니다.

예시 SQL은 다음과 같습니다.

```sql
update public.profiles
set name = '직원명', employee_number = '260001', department = '상담지원팀', role = 'employee'
where email = 'staff@example.org';
```

비활성 직원은 `is_active = false`로 바꿉니다. 계정과 기존 기록을 삭제하지 않습니다.

## 월별 자동 판정과 마감

출근과 퇴근 시각은 서버 시각을 기준으로 저장됩니다. 출근 기록 때 지각 여부를, 퇴근 기록 때 근무시간 충족 여부를 확인합니다. 외근, 회의, 교육, 상담 등 업무내용과 근무 중 이동은 기록하지 않습니다. 출퇴근 순간이 사업장 안인지 밖인지만 확인해 일반 출근, 직출, 일반 퇴근, 직퇴로 자동 구분합니다. 자정이 지난 뒤 퇴근하면 24시간 이내의 전날 미퇴근 기록을 찾아 같은 근무일의 퇴근으로 저장합니다.

당일 출장은 출장지에서 실제 업무를 시작하고 마치는 시각에 출퇴근을 기록합니다. 숙박 출장처럼 여러 날 지속되는 승인 출장과 기타 승인 예외 근무는 관리자가 기간을 등록할 수 있습니다. 해당 기간에는 직원이 매일 출퇴근 버튼을 누르지 않아도 정상 근무로 인정하며, 등록과 취소는 변경 이력에 보존합니다.

`recalculate_attendance_month` 함수는 지난 근무일의 출근과 퇴근 누락, 결근을 계산합니다. 월 마감 때 자동으로 실행됩니다. 공휴일과 직원별 예외 일정이 정확히 입력됐는지 먼저 확인해야 합니다.

월 마감 순서는 다음과 같습니다.

1. 관리자 월별 근태에서 대상 월을 선택합니다.
2. 위치 확인 필요, 누락, 지각, 조퇴 기록을 확인합니다.
3. 대기 중인 수정 요청을 모두 처리합니다.
4. CSV 또는 엑셀을 내려받아 검토합니다.
5. 월 마감을 실행합니다.
6. 마감 해제가 필요하면 최고관리자가 사유를 입력해 처리합니다.

월 마감은 선택한 달의 누락과 결근을 다시 계산하고, 해당 달의 기록을 확정해 일반 수정과 삭제, 수정 요청 승인을 막는 기능입니다. 마감 여부는 월별 근태 화면에 표시됩니다. 실수로 마감한 경우 최고관리자가 사유를 5자 이상 남기고 월 마감 해제를 누르면 다시 수정할 수 있습니다. 마감과 해제는 변경 이력에 남습니다.

## 내보내기

관리자 월별 근태 화면에서 다음 형식을 사용할 수 있습니다.

- CSV, UTF-8 BOM을 포함해 한글 깨짐을 줄였습니다.
- 엑셀, 월간 기록과 직원별 요약 시트를 포함합니다.
- 인쇄 또는 PDF, 브라우저의 인쇄 기능에서 PDF 저장을 선택합니다.

변경 이력은 월별로 조회하며, 선택한 달의 이력만 CSV 또는 엑셀로 내려받습니다.

## 보안 운영

- Supabase 서비스 역할 키를 브라우저와 저장소에 넣지 않습니다.
- 운영 도메인만 Supabase 인증 Redirect URL로 허용합니다.

- 데이터베이스 정책을 변경한 뒤에는 직원 계정으로 다른 직원 기록이 보이지 않는지 확인합니다.

- [ ] 현재 비밀번호를 확인한 뒤 본인 비밀번호를 변경할 수 있다.

- [ ] 최고관리자가 새 직원 계정을 만들면 로그인 목록에 자동으로 표시된다.
- [ ] 퇴사 처리한 직원은 로그인 목록에서 숨겨지고 기존 기록은 보존된다.
- [ ] 퇴사자를 재활성화하면 로그인 목록에 다시 표시된다.
- [ ] CSV와 엑셀 파일의 한글이 깨지지 않는다.
- [ ] 인쇄 화면에 메뉴와 버튼이 제외된다.

### 부관리자

- [ ] 직원 계정과 출퇴근 기능을 그대로 사용한다.
- [ ] 전체 직원의 월별 근태현황과 변경이력을 조회한다.
- [ ] CSV, 엑셀, 인쇄 자료를 내려받는다.
- [ ] 승인, 수정, 삭제, 월 마감, 설정 기능에는 접근하지 못한다.

### 보안

- [ ] 브라우저 번들에 서비스 역할 키가 없다.
- [ ] 다른 직원 ID를 직접 요청해도 자료가 반환되지 않는다.
- [ ] 일반 관리자가 `attendance_locations`를 조회할 수 없다.
- [ ] 감사 로그 삭제 요청이 거부된다.
- [ ] 비활성 직원의 출퇴근 RPC가 거부된다.
- [ ] 월 마감 뒤 수정 RPC가 거부된다.

## 현재 1차 버전의 범위

다음은 안정적인 운영을 위해 2차 작업으로 분리했습니다.

- 첨부파일 업로드와 악성 파일 검사
- 직원별 반복 근무표 편집 화면
- 조직 메일 자동 알림
- 다중 사업장과 부서별 세부 권한

첨부파일 선택란은 개인정보 최소수집을 위해 현재 비활성화돼 있습니다. 필요성이 확정되면 Supabase Storage의 비공개 버킷과 파일 접근 정책을 먼저 설계한 뒤 활성화합니다.
